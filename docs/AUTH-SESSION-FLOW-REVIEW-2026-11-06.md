# 登录会话与游戏启动流程复查（2026-11-06）

## 实测证据与结论边界

- 原运行中的 authlib-injector 已正常注入；游戏令牌与保存的会话一致，认证服务器对两者均返回 403（Invalid AccessToken）。这证明进服时会话无效，不能单凭这一结果证明启动前也已失效。
- 后续重新登录的会话，认证服务器返回 204。检查与回归测试未刷新、吊销或覆盖用户当前的真实会话。
- 缺少原启动过程逐步认证结果，无法区分当时是刷新结果本身无效、校验后的失效，还是其他客户端操作造成的吊销。

## 已确认的代码缺口及本地修复

1. 启动恢复和启动前校验原本各自实现刷新，均直接信任 refresh 的 200 响应。现在共用会话门控；检查返回字段、角色一致性，并再次调用 validate。只有新令牌通过校验才能交给游戏或替换保存的会话。
2. 原校验在资源安装之前。现在资源准备完成后才进入认证门控；构建进程、准备共享目录之后，在 Process.Start 前再次校验，不通过则清理共享状态并阻止启动。
3. 不同实例可并发启动，原本各自持有旧会话；UI 要等游戏窗口出现后才更新。现在序列化认证到进程启动的阶段，并保留已验证的刷新替换关系；即便后续启动失败或 UI 尚未收到结果，也不会重复刷新旧令牌。等待游戏窗口在门控之外。
4. 多角色登录原本只在本地指定角色。现在无 selectedProfile 的认证结果会通过 refresh 向服务器绑定所选角色，确认服务器返回角色及令牌有效性后才进入主窗口。
5. 刷新尊重不记住登录；主动取消认证请求保留取消语义，不再误报为超时。

构建：`dotnet build tests/Bottom.Tests/Bottom.Tests.csproj -c Release --artifacts-path <临时目录>`。

测试：生成的 `CMUmcl.LauncherSettings.Tests.exe`，54 项检查全部通过，其中新增 34 项认证检查；资源下载与更新回归另有 47 项通过。覆盖有效令牌不刷新、无效令牌刷新与保存、刷新后仍无效、缺少令牌或角色、角色错配、并发刷新、等待取消、启动失败后复用新会话、不记住登录、进程启动前失效、网络异常与角色绑定请求。

二次复查增加原子保存条件，避免刷新结果覆盖退出登录或其他新登录；保留刷新已返回但复验被取消的新令牌，仅在后续复验通过后保存、使用。单角色与多角色的真实登录完成方法也纳入测试。

测试已进入现有 GitHub Actions 的 Bottom.Tests 回归入口。修复版版本号为 0.3.48.15，计划经 GitHub Actions 发布；发布与真实账号验收结果将另行记录。构建缓存与日志保留在工作区 `.tmp/auth-session-fix`。

这些检查缩小了校验与启动之间的窗口，不能保证游戏运行后令牌永不被其他登录、管理员或认证服务器吊销。
